# 业务设计 Agent：多团队、多产物架构

**决策状态：待试点。** 这是从业务角色出发的目标架构，不是给现有命令套一层接口。原型是已有能力；高保真、演示、功能验证和视觉验收是独立可交付的扩展。系统不内置金融业务、特定页面版本制度、设计风格或默认品牌。

## 1. 从工作日出发

| 角色和时点 | 发起动作 | 交付与决定 |
|---|---|---|
| 设计负责人接入一条新产品线 | 转发已有规范和两个代表屏，说明哪些必须遵守 | 核对 Agent 的理解卡，批准团队规范版本；不写代码 |
| **业务设计人员起草 PRD（第一棒）** | **在工作区迭代目标、现状截图/Word/Figma 资料、外部反馈与内部评审、线上搜索细节及参考范本** | **同源产出美观易读的 Figma 单页 PRD（含简单流程展示与低保真原型图）与可编辑 `.docx`；详见 [PRD 工作流](PRD-WORKFLOW.md)** |
| 产品设计师评估流程 | 从需求或 PRD 提取角色、主路径和一个有意义的分支 | 业务方点通低保真原型，决定流程是否成立 |
| UI 设计师交付开发 | 选已确认流程或现有参考稿，附真实长度的文案与状态 | 交可编辑的高保真源稿及组件引用，负责人验收，不以效果图替代源稿 |
| 业务负责人汇报 | 选观众和要说明的决策，如“这次减少了哪一步” | 在会议上使用一份可打开的演示；无须先购买视频能力或生成全部格式 |
| QA 在预发验收 | 给测试环境、账号角色、可重复使用的样例与预期 | 浏览器逐步执行，交有实测证据的功能报告 |
| 设计师跟研发走查 | 指定已签收设计屏及相应网页状态 | 对图报告定位到具体区域，研发修复后在同一基准复验 |

后三种都可独立发起。例如 QA 可直接拿现成网页和业务预期跑验收，不需要先在本平台生成设计稿。

## 2. 只分四块，一开始不拆服务

```text
团队规范资料 → 规范入口 → 已确认团队卡（按团队、产品、端、版本）
                                 ↓
需求 / 现有设计 / 测试地址 → 任务协调器 → 固定上下文 + 业务流程
                                           ↓ 只选所需场景
    PRD 编写 | 原型设计 | 高保真设计 | 主流程演示 | 功能验证 | 视觉对图
                                           ↓
    Word 读写/导出 | Figma 读写/导出 | HTML 输出 | Chrome DevTools MCP | 图像比较
                                           ↓
                      成品、证据、报告与签收记录
```

* **规范入口**负责读取资料和确认解释，不创建设计稿。保留资料原文和来源版本，模型提取的是候选规则；人工确认的内容才参与正式交付。
* **任务协调器**负责选择团队版本、业务路径、目标和产物，调用场景并保存结果。它不懂颜色、不发浏览器点击、不解释某客户的审批制度。初期本机进程和目录足够，不做工作流引擎。
* **场景模块**决定“这项产物需要什么输入、调用哪些能力、交什么证据”。一个模块可以只读，不需要所有模块共用一个通用 `execute` 脚本。
* **工具适配器**是唯一了解外部工具细节的一层。Figma 读写、Chrome 会话、图像比较分别适配；Git、聊天、文档、设计库均可以是资料来源，无需同时实现全部连接器。MCP 是外部调用协议，不是业务规则格式。Claude Code、Antigravity 或团队的 DeepSeek 宿主应能提交同一种任务并拿回同一结构的结果；配置、身份和实测兼容性分别记录。外部宿主可调用提交任务、运行场景、读取产物三个入口；不用 MCP 时可用本地命令，核心不反向依赖宿主。

## 3. 数据约定：共享业务事实，不共享一棵万能 UI 树

| 记录 | 必要内容与用途 |
|---|---|
| `TeamProfile` 团队卡 | `team/product/surface/revision`、确认人、每条规则的适用场景/强制或偏好/来源定位、资产引用、工作区及评审约定。页面、组件、图片、文本都可做参考，区分“可编辑资产”和“仅视觉参考” |
| `Brief` 任务卡 | 团队版本、目标角色、目的、不可改项、要交的产物、基准与目标、确认的本单例外。执行时锁定版本；不从同名的别组规范回退 |
| `Journey` 业务路径 | 步骤 ID、角色、前置状态、动作、预期可见结果、下一步或分支。如 `approve: 主管＋待审 → 点批准 → 已处理`。只对有流程的任务填写；单屏对图可直接指定一个状态 |
| `Binding` 场景定位 | 同一步分别对应哪个 Figma 节点、浏览器可访问名称或演示镜头。业务步骤不保存像素坐标、浏览器内部 UID 或视频时间码；实际定位随目标版本生成 |
| `Artifact` / `Evidence` | 成品类型、可打开位置、团队/任务、来源设计或构建版本、步骤或状态、实测环境和证据。报告关联的是稳定的产物版本，不是一个永远指向最新的链接 |

**规则怎么选：**先按团队、产品、端和场景筛选。业务行为由已确认需求负责；组件、品牌和稿件管理由对应团队规则负责。已批准的任务例外只覆盖指明的规则；单纯的“偏好”可被明确任务要求取代。两条硬规则冲突只问冲突项，列出原文和来源，不靠“最后读到的覆盖”。规范缺失可以做明确标记的草案，但不出符合性结论。只在接入、真实冲突和团队规定的签收点找人，不逐步弹窗。

**落盘与交接：**首版按团队放资料和已确认档案，按任务放锁定快照、输入引用、各场景成品与报告。访问资料沿用源系统权限；工程中的团队标识不是权限机制。业务人员从需求单上的一个入口看到当前签收版本。资料有变时新开版本；旧截图仍可查看，但不替新设计或新构建作证。首版不用数据库、规则语言或公司级组件中台。

## 4. 各场景的完成条件

| 场景 | 最小输入 → 执行 → 可交付物 | 如何验收 |
|---|---|---|
| PRD 编写（[工作流细则](PRD-WORKFLOW.md)） | 需求目标 + 已有资料（Word/Figma/现状图/反馈/评审/范本） → 五选项多轮迭代（含线上搜索思考补全细节）、梳理最短流程与低保真原型屏 → 同源 Figma 单页 PRD + 可编辑 `.docx` | 双端内容一致且整份 PRD 聚合在单个 Figma 页内；现状图与原型屏严格区分（缺图写待补，搜索建议标待确认）；每屏标明入口、动作与结果 |
| 原型 | 角色、目标和关键状态 → 生成线框或改测试稿，绑定导航和状态切换 → 可点击原型及入口 | 从入口走通主路径和本次涉及的分支；注明模拟行为；评审者不用作者口头指路 |
| 高保真 | 已确认流程或已有屏幕、团队组件/样式、目标尺寸和文案 → 复用真实组件，填充状态，检查布局 → 可编辑源稿、状态清单和预览 | 读回组件来源和布局；真实长度文案无裁切，交互/禁用/空态按需交付。缺必要品牌资产时给草案，不宣称完成品牌签收 |
| 主流程演示 | 观众、叙事目标、流程和指定版本素材 → 每一步生成“要说什么／展示什么／来源”分镜 → 一种适用媒介 | 需观众自己点选用 HTML，逐页讲解用 slides，无人操作或异步观看用视频；检查可打开、关键动作顺序及观看效果。基于原型的演示标明模拟，不冒充线上录屏。先交 HTML；其他格式复用分镜，不强求同版式 |
| 页面功能验证 | 授权测试 URL、角色、固定数据、预期 → Chrome DevTools MCP 新建隔离浏览器会话，取快照、按语义定位、操作、重新取快照断言 → 逐步报告 | 每条列前置、预期、实际、通过/失败/未测和证据；已执行但实际不符才判失败，缺环境或不可观察写未测并说明。网络/控制台只用于解释；页面显示不证明服务端授权。仅在测试环境操作可复位的测试数据 |
| 设计还原对图 | **已批准的** Figma 版本和 Frame、同状态页面、视口与 DPR → 导出设计、Chrome 截屏、对齐画布、生成差异区域 → 设计/实际/差异三图及报告 | 固定主题、语言、字体、数据、滚动和动画；先检查连续两张实测图稳定。记录遮罩区域及理由、像素阈值和容差来源；宽高不一致先报尺寸问题，不强拉伸。分别报文字、布局、颜色等具体偏差，人工判定设计意图。没有设计基准只能做回归比较，不叫还原验收 |

**报告例：**`approve / 待审 / 主管`：预期状态文字「已处理」，实际「待审」，失败；附操作前后快照、构建号和重现入口。视觉项独立列 `退款表头 / 桌面宽度`：基准、实测、差异热区、偏移量和设计师结论。整页低差异率不能抵消关键按钮被裁切。功能通过不自动让视觉通过，发布决定也不由模型代签。

**Computer Use 的预留边界：**功能执行器接受“观察界面、执行动作、捕获证据”三个能力。当前仅计划支持 Chrome DevTools MCP；未来 Computer Use 返回画面与可见文本，不能假装有 DOM、网络记录或稳定节点 ID。场景发现证据能力不足时明确未测，不静默切换到桌面点击。本期不新增桌面权限或实现第二驱动。

## 5. 扩展和上线顺序

| 阶段 | 先交什么 | 进入下一阶段的实证 |
|---|---|---|
| A 双团队原型试点 | 两位设计师各交一份真实资料，确认理解卡，分别做一条原型主路径 | 不改核心就采用两种不同组件和评审方式；换人能打开并走通原型；记下误读的规范及返工原因 |
| B 高保真与演示 | 在其中一单补高保真，再用同一版状态生成 HTML 分镜演示 | 源稿可编辑、组件可追溯；业务负责人能独立看懂演示。如真实客户需要离线汇报，再加 slides 或视频导出 |
| C 浏览器功能验收 | 接入授权预发环境、测试数据与 Chrome DevTools MCP，产出首份功能报告 | 对已知正确路径和一个故意不满足的预期给出相反结论；失败步骤可重放；换一个团队只换资料和定位 |
| D 对图与推广 | 对同状态真实设计和网页做一次比较，研发修复后复验 | 报告能指出已知偏差、忽略获批的动态区、修复后消失。由设计师确认可接受容差；再验证实际使用的宿主组合 |

每次扩展先问：是团队特有的要求（写进团队卡），新的交付物（加场景），还是不同工具完成同一动作（加适配器）？只有重复出现的需要才进共享层。**不做**所有业务共用的页面命名、预置审美 Tokens、五件套强制流水线、无限层级规则继承或多格式渲染平台。
