# 角色一 · 业务设计人员：迭代编写 PRD、原型图与流程展示

业务设计人员是需求进入业务开发链路的第一棒：基于手头零散的需求描述、Word 文档、Figma 稿、现状截图与各方反馈，梳理清楚目标与边界、画出产品原型图与简单流程展示，最终同时产出一页**美观易读的 Figma 单页 PRD** 和一份**结构同源的可编辑 Word 文档（`.docx`）**，供后续视觉设计、研发实现与测试验收直接承接。

---

## 1. 启动分流（设定工作区后第一步）

用户在工作区明确要使用 `figma-agent` 但尚未指定具体任务时，Agent 第一步先询问：

> “这次想让我帮你做什么？
> 1. 开发或更新产品 PRD（含产品原型图与简单流程展示）
> 2. 绘制或迭代可交互原型
> 3. 出高保真视觉稿
> 4. 执行页面功能验证或视觉还原对图”

若用户已直接表明要“写 PRD / 开发 PRD / 更新这份 PRD”，不再重复追问角色，直接在当前工作区初始化需求目录（例如 `<workspace>/prd/<需求简称>/`），进入下方的 **PRD 五选项迭代循环**。

---

## 2. PRD 五选项反复迭代循环

整个 PRD 编写过程采用「小步迭代、随时补充、按需检索深化」的对话循环。**每一轮处理完用户的输入后**，Agent 先用简短摘要回显当前进度（已定需求目标、已读取资料/截图数量、已梳理流程步数与原型屏数、待确认项），然后反复给出以下选项供用户继续推进：

| 选项 | 适用动作 | Agent 执行规范 |
|---|---|---|
| **1. 设定、修改或补充需求目标** | 明确给谁用、解决什么痛点、核心业务目标与明确不做项（Non-Goals） | 提炼可衡量的目标条目与排除范围；目标发生变更时同步提示受影响的流程与原型屏。 |
| **2. 提供或补充其他资料** | 投喂需求描述、Word 文档、Figma 页面、现状截图、外部用户/客服反馈、内部评审意见等（无需一次备齐） | **收到即真实读取**，回复「读到了什么、理解到什么、哪些内容未能读出」。严格区分「现状事实」「已拍板结论」「外部提议」「内部待定意见」；意见相反时只追问影响方案的那一点，不替负责人拍板，未经允许不改用户原话。 |
| **3. 基于已有材料进行线上搜索和思考，帮助设计需求细节** | **条件启用：仅在已提供/设定「需求目标」后开放选择**（未设目标时提示先完成选项 1 或 5） | 围绕已设定的需求目标与现状材料，开展线上搜索（同类产品成熟交互范式、无障碍与防呆惯例）及结构化推演，主动补全主流程之外易遗漏的细节（空态、取消与回退、重开/跨页状态同步、存储或网络异常降级、临界长文案）。所有推演内容显式标记为 `[Agent 检索与推演建议 · 待确认]`，由业务设计人员选择采纳或调整，绝不冒充原始需求或真实用户反馈。 |
| **4. 提供其他 PRD 范本** | 上传或指定团队过往优秀的 Word / Markdown / Figma PRD 范本 | 解析提取范本的章节骨架、字段颗粒度、表格列定义与验收写法，锁定为本单双端输出的结构模板；未提供时使用标准六段式清晰模板并标明“通用默认模板”。 |
| **5. 手动输入或修改需求** | 直接口述或输入具体业务规则、增删流程步骤、调整某屏原型控件或文案 | 即时合入当前结构化 PRD 草稿（`prd-source.json`），回显本次改动点。 |
| **6. 预览并输出双端 PRD** | 用户表示“资料齐了 / 可以出稿 / 先出一版草稿” | 先输出**成稿前预览**（核心目标、简单流程链、原型屏列表、验收标准条数与待确认项；草稿明确标“草稿”），确认目标位置后同源生成 Figma 单页与 Word 文档。 |
| **0. 退出当前 PRD 模式** | 用户想切换到原型图设计、视觉出稿或页面验证等其他角色模式 | 保存当前 `prd-source.json` 进度，退回**顶层主菜单**供用户自由切换角色或任务。 |

### PRD 生成完成后的无缝衔接菜单
当执行完 **选项 6（完成双端 PRD 输出）** 后，Agent 主动给出下一步衔接选择，方便业务设计人员一气呵成完成可点击原型图：
> 1. **继续修改或补充当前 PRD**
> 2. **紧接着基于这份 PRD 生成可操作预览原型图**（自动继承本单目标、流程与验收依据，进入 [可操作原型图模式](PROTOTYPE-WORKFLOW.md)）
> 0. **退出当前模式，返回主菜单切换其他角色或任务**

> 可通过 `./fimg prd menu-state <prd-source.json>`（或 MCP 工具 `prd_menu_state`）检查当前草稿完整度及选项 3 是否已满足解锁条件。

## 3. 多源资料读取细则

| 资料类型 | Agent 具体处理方式 |
|---|---|
| **Word 文档（`.docx` / `.doc`）或参考范本** | 运行 `./fimg prd inspect <文档路径> --extract-dir <工作区材料目录>`（或 MCP 工具 `prd_inspect_docx`，纯 Node 零 Python 依赖）：自动提取章节大纲（可直接作为选项 4 的范本骨架）、正文段落、全部表格、`word/comments.xml` 评审批注，并将 `word/media/*` 内嵌截图解出保存。旧版 `.doc` 在 macOS 下自动经 `textutil` 转换后解析；无法直接读取的 OLE 嵌入附件或离线外链图片，必须在回执中逐条列出，不得当成已读。 |
| **飞书云文档（URL / Token）** | 若已配置飞书 CLI（`lark-cli auth status` 通过），运行 `lark-cli docs +fetch --api-version v2 --doc "<飞书文档URL或Token>"` 直接拉取在线需求全文或评审记录；未登录时提示用户直接运行 `lark-cli auth login` 在浏览器确认授权后再拉取。 |
| **Figma 文档或现状页面截图** | 先向用户确认是「只读参考稿」还是「最终写入目标」。只读查看指定页/Frame 的节点树与导出图，每张现状图标明来源文件、版本、屏幕与状态。打不开的外部链接直接请用户开放权限或提供导出图，绝不凭链接名称猜测画面。 |
| **外部反馈与内部评审意见** | 逐条保留原始出处与原意，标记采纳状态（`已确认采纳` / `待确认` / `暂不纳入`）及对界面或规则的具体影响，写入 PRD 的输入溯源台账。 |

## 4. 简单流程展示与产品原型图设计准则

1. **简单流程展示（先讲清最短闭环，再列关键分支）**
   - 主路径用一条最短操作链表达（例如：`[01] 阅读详情并收藏 → [02] 进入我的收藏核对 → [03] 返回或重开保持状态 → [04] 取消收藏并复查空态`），每一步写清**角色、触发操作、预期可见结果**。
   - 将首次空态、取消回退、权限/存储异常降级等单独列为**关键分支条**，既不淹没主干，也不漏掉边界。
2. **产品原型图（围绕状态变化画低保真线框，评审免口头指路）**
   - 针对核心页面及变化状态（如默认态、激活态、列表有内容与空状态）绘制结构清晰的低保真线框屏（包含顶栏导航、主体内容块、分段切换、列表/空态占位、主次操作按钮与异常提示位）。
   - **每张原型屏下方固定附带「前置入口 / 本屏动作 / 状态结果」交互说明卡**；缺现状截图时明确标「现状截图待补充」，绝不拿新绘制的原型图冒充旧版现状图。

## 5. 三端同源产出：美观易读的 Figma 单页 + Word 文档 + 飞书云文档同步

业务设计人员全程只需自然对话，由 Agent 维护统一数据源 `<prd-source.json>`（字段示例见 [`examples/app-delivery/prd-source.json`](../examples/app-delivery/prd-source.json)）并执行以下交付步骤：

1. **同源构建本地三件套产物（纯 Node.js，零 Python / 零第三方依赖）**
   ```bash
   ./fimg prd export <工作区>/prd-source.json <交付目录>
   # 或直接调用 MCP 工具 prd_export_bundle
   ```
   一次生成三份内容严格一致的交付物：
   - **`<交付目录>/PRD.docx`**：标准可编辑 Word 文档，内置中文排版样式与导航大纲层级，包含元信息总表、需求目标与不做范围、**内嵌真实 PNG/JPEG 现状截图**、多源反馈与搜索建议台账、主流程与分支表、**文字可直接编辑的产品原型框线示意卡**、功能细则与验收标准表。
   - **`<交付目录>/PRD.figma.json`**：单页宽幅看板规格（`PRD 单页看板 · <标题>`），按清晰视觉层级在一个页面内纵向组织六大分区：`00 深色总览头卡` → `01 目标与边界双栏卡` → `02 现状截图画廊与反馈溯源` → `03 横向可视化流程链与分支卡` → `04 多屏并排产品原型线框展示台` → `05 需求细则、验收标准表与待确认项`。**绝不按章节拆分成多个 Figma Page。**
   - **`<交付目录>/PRD.md`**：结构化 Markdown 文本，用于同步至飞书云文档。
2. **同步到飞书云文档（新建或就地更新）**
   ```bash
   # 新建飞书云文档
   ./fimg prd sync-feishu <交付目录>/PRD.md --title "<PRD 标题>"
   # 更新已有飞书云文档（传入已有文档 URL 或 Token，不重复建空文档）
   ./fimg prd sync-feishu <交付目录>/PRD.md --doc "<已有飞书文档URL>"
   # 或直接调用 MCP 工具 prd_sync_feishu
   ```
   若用户尚未登录飞书 CLI，直接提示或拉起 `lark-cli auth login` 在浏览器完成账号授权（仅当未绑定应用时再运行 `lark-cli config init --new`，参考 [飞书 CLI 官方文档](https://open.feishu.cn/document/mcp_open_tools/feishu-cli-let-ai-actually-do-your-work-in-feishu)）后重试，并先交付本地 Word 与 Figma 产物。
2. **静态校验 Figma 单页规格**
   ```bash
   ./fimg check <交付目录>/PRD.figma.json
   ```
   确认 `问题数: 0`（无非法尺寸、无文本漏宽溢出、无容器透明度污染）。
3. **安全写入目标 Figma 单页并核对**
   - 先运行 `./fimg status` 与页面检查，向用户确认目标文件与页面名称：
     - **写入全新 PRD 页**：经用户确认页名后执行 `./fimg render <交付目录>/PRD.figma.json --page "<确认的页名>"`。
     - **更新已有同名 PRD 页**：先用 `./fimg list --page "<页名>"` / `dump` 读取现有节点结构，再用 `patch` / `insert` 就地更新变动区块，**严禁再次整页 `render` 清空用户已有画布或批注**。
   - 写入后用 `list` / `dump` 读回标题与分区节点，必要时导出 PNG 核对排版可读性。
4. **诚实回传交付结果**
   - 双端均完成后，返回 `PRD.docx` 本地路径与实际 Figma 页面位置。
   - 若当前本地桥或 Figma 插件未连接，先交付已生成的 `PRD.docx` 和通过校验的 `PRD.figma.json`，明确说明“Word 文档已生成；Figma 单页规格已就绪，尚未写入 Figma 画布”，绝不把离线规格报成双端已落盘。
