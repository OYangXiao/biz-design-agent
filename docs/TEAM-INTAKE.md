# 给设计师：怎样让 Agent 采用你们的规范

不需要写 JSON、节点 ID、插件名或提示词。第一次使用时提供一张团队卡，以后提需求只交任务卡。可以用聊天、普通文档或表单填写；已有规范直接给链接和章节，不必重录。以下是拟议的使用体验，当前没有上线表单或自动导入器。

## 团队卡（可直接填写）

| 问题 | 你们的答案 |
|---|---|
| 哪个团队、哪个产品、哪一端？谁确认规范？ | |
| 最该参考哪份设计系统或已发布稿？给链接，指出具体组件、屏幕或章节 | |
| 哪些是**必须**，哪些只是**优先**？最好给一个正例或反例 | |
| 有哪些常用业务角色、状态、不能改的文案？ | |
| 通常在哪里改、怎样交给谁评审？有特殊演示或验收要求吗？ | |

可以只给一份可访问的 Figma 参考稿，加一句“表格沿用这里的列表行，不要照搬侧栏”。Agent 应先回一张**理解卡**：规则原文、适用范围、来源位置、一个应用示例、未能读取的资料。由指定设计负责人纠正并确认后，保存为该团队的一个版本。截图可做视觉参考，不自动成为可复用组件；给了链接也不代表已成功读取。

## 单次任务卡

> 团队与产品：____。给谁用：____。在什么条件下做什么，做到哪一步算完成：____。参考和目标位置：____。本次要交：原型／设计稿／演示／功能报告／对图报告（可单选）。哪些不动：____。由谁看、希望据此做什么决定：____。

只有选择浏览器验证时才要测试 URL、环境版本、角色与样例数据；只有选择对图时才要指定设计版本、屏幕、视口和状态；演示才问观众、时长或媒介偏好。不在每单重复问品牌色、发布制度等团队卡已有的信息。

## 两个互不继承的示例（虚构，不是默认值）

| | 阅读 App | 社区活动 App |
|---|---|---|
| 团队提供什么 | “沿用文章页的排版。收藏后的按钮要明确写『已收藏』；别只变颜色。” | “报名沿用活动库的底部操作条。每轮用独立评审副本，批注直接放在稿旁。” |
| 本次需求 | 读者在文章页点收藏，下次能从「我的收藏」找到它 | 访客进入活动详情、报名并看见确认；已满员时展示原有文案，不显示报名按钮 |
| 理解卡里应有 | 明确详情页、收藏列表共用同一份收藏状态；列清收藏和取消后各页长什么样 | 独立副本不是强制 beta 命名；底部操作条引用活动库，不借用阅读 App 的按钮 |
| 签收依据 | 业务设计走一遍收藏和取消，美工看对图，测试复查返回和重开 | 设计师检查源稿组件和完成态；业务方能打开演示，区分报名成功与满员 |

**更新规范：**补一句“从下一轮起用新版组件”，附来源。Agent 只展示变化的规则、受影响的场景和旧版仍在使用的任务；确认后出新版本。正在评审的任务不自动迁移。需求明确写“这次例外”时先找该规则负责人确认，只记录在本单，不污染团队卡。

## 被退回来一次，怎样让下一位接得住？

不用重填整单。在原单补一条：「用哪个版本和身份打开哪份数据？本来应看到什么，实际看到什么？修完照哪条路径再看？」把能打开的入口和原图一并贴上。比如“不显示”就是连灰按钮也没有，不能只写“不能操作”。如果要求交班后再开，顺手说清楚是不是换账号、浏览器或设备；没测过的情况不要写成通过。对图时写明哪一屏、哪个尺寸；每一版留下自己的结果，不覆盖上次的记录。

这不是审批表，只有发生误解时才补需要的几句话。[看阅读 App 团队怎样退回和复查](../examples/app-delivery/index.html#results)。
